# سير العمل — الجولة 68

**التاريخ:** 19 سبتمبر 2026 · **النوع:** ميزة (طلب المالك المؤجل من المحادثة)
**سطح العمل:** صفحة الإدخال → تاب الأوفر تايم (واجهة + API + عمود DB).

## الخلاصة في سطر

**واجهة تسجيل الأوفر تايم بقت زي تسجيل الإنتاج:** شريطا الخط/القسم
بنقر مباشر (نفس مكونات R58) + التاريخ الافتراضي امبارس + خانة
الأشخاص الإضافيين (اللي مش مسجلين كود/اسم في الاتزان): عدد +
ساعات الشخص — بتتضاف على المختارين بالاسم، لكل قسم وخط، والحساب
مرئي في شريط إجمالي + ملخص قسم/خط. E2E **97/97**.

## 1) نموذج البيانات

`marib_overtime.extra_count INT NOT NULL DEFAULT 0` (BOOT_VER 59→68،
ALTER idempotent). الصف العادي (بالاسم) extra_count=0 · صف
الإضافيين = موظف فاضي + extra_count=N والـ hours فيه = ساعات
الشخص الواحد (إجمالي الصف = N × hours).

## 2) الـ API (`/api/entries/overtime`)

- **POST:** حفظ واحد ممكن يخرّج صفين — صف الشخص المسمّى (لو اتختار)
  + صف الإضافيين (لو عدد>0) — **في withTransaction واحدة** (مفيش نص
  حفظ لو التاني فشل). التحقق: إضافيين لوحدهم كفاية (كانت 400 قبل
  كده) · 0<ساعات≤24 لكل جزء · سقف العدد 500. الرد متوافق للخلف:
  `id`/`matched` (بيتكلموا عن الصف الأول) + `ids` + `extra_count`.
- **GET:** بيرجّع `extra_count` + `is_extra` — و`matched:true`
  لصفوف الإضافيين (مش «غير متطابق» — ده نوع صف مقصود).
- audit لكل صف اتعمل (create + سياق: emp أو extra).

## 3) الواجهة (`app_entries.js` + `i18n_dict.js` + `app.css`)

- **الفورم:** `entYesterday()` (نفس منطق الإنتاج) + `entStripRow`
  للخط فوق والقسم تحت (نفس مكونات R58 — مفيش تكرار CSS) + الكومبوبوكس
  زي ما هو + خانة الإضافيين (عدد + ساعاتهم) بتون dashed مميز + هيُنت.
- **الجدول:** صف الإضافيين بيتعرض بالحساب المرئي «3 × 2 = 6» وشارة
  «إضافي» — والقسم بيعرض الخط جنبه (`.faint`).
- **شريط الإجمالي** (`ent-ot-sum`): بالاسم · إضافيين · الأشخاص ·
  الساعات — الشهر كله.
- **ملخص القسم والخط** (`ent-ot-bd` details + جدول): «لكل قسم وخط
  عشان يحسب صح» — القسم · الخط · بالاسم · إضافيين · الإجمالي · الساعات.
- 9 مفاتيح ترجمة AR/EN/TR (`ent_ot_*`) + CSS بالثيمين (درس R54).

## 4) باج كامن اتصلح في بنية الاختبار (اكتشاف الجولة)

أول تشغيلة E2E طلّعت 5 فشل في مقارنات XLSX — **مش من الجولة**:
التصدير بيكتب «تصدير YYYY-MM-DD» بختم اليوم في خلية العنوان،
وكل الجولات قبل كده اشتغلت نفس يوم التقاط الـ baselines (17
سبتمبر) فالباج مستخبي. الإصلاح بعقيدة R59 (الطابع هوية مش بيانات):
`e2e_cmp_xlsx` بيطبّع تاريخ العنوان في 4 سياقات معروفة بس (تصدير ·
تيمبلت الاتزان · تيمبلت الغياب · تيمبلت عقود الـ PO) — وأي تاريخ
بيانات تاني بيفضل فاضح. **الكَناري أثبت المقارنة لسه قوية:**
(1) تاريخ مختلف = متطابق ✓ (2) قيمة بيانات متشوهة (810→999) =
متصطادة ✓ (3) تاريخ في سياق غير معروف = متصطاد ✓
(`scripts/r68_canary.py` خارج الريبو).

## 5) الإثبات

- **E2E 97/97 EXIT=0** — 11 JSON + 5 XLSX متطابقة بالبايت مع
  الـ baselines (صفر تغيير سلوك) + كل حراس الخلفية الدائمة

- BOOT_VER 68 اختبر مسار الترحيل الفعلي (bootstrap من الصفر).

## دروس الجولة

1. **البايت-كومباريزون لازم يعرف المتغير بالطبيعة قبل يوم الفشل** —
   باج تاريخ العنوان كان مستخبي 6 جولات لأن كل الجولات اشتغلت
   نفس اليوم. لما تضيف تطبيع: اعمل كَناري يثبت إن المقارنة لسه
   بتعض.
2. **«حط |» في R67 و«زي الإنتاج» في R68 نفس الدرس:** قبل ما تبني
   جديد، بص في الموجود — شريطا R58 والكومبوبوكس اتعاد استخدامهم
   حرفيًا (صفر CSS جديد للأشرطة).
3. **الحفظ المركب يتربط بمعاملة واحدة** — صفين من حفظ واحد من غير
   withTransaction كان هيسيب نص حفظ لو التاني فشل.
