## أولا — التشخيص: كان عندك حق، زراير وخلاص

المراجعة الكاملة لنظام الصلاحيات (R46) كشفت فجوتين حقيقيتين:

### 1. السيرفر: أهم مسارين في الموقع كانوا من غير أي فحص صلاحيات

| المسار | الحارس قبل R55 | المعنى |
|---|---|---|
| `GET /api/data` | `requireUser` فقط | **أي يوزر داخل بياخد كل بيانات اللوحة** — «مخفي» لـ Nada معناها صفر |
| `POST /api/data` | `requireRoleBody("admin")` | بالدور مش بالصلاحية: يوزر ممنوح «رفع البيانات» كان مرفوض، وأدمن متخصوم منه «رفع البيانات» كان بيرفع عادي |
| `GET /api/manpower` | `requireUser` فقط | الاتزان مفتوح لأي يوزر |
| `POST /api/manpower` | `requireRoleBody("admin")` | نفس قصة الدور — منح «تعديل الاتزان» ليوزر كان بيتجاهل |
| `GET /api/manpower/export` | `requireUser` فقط | منع التصدير كان مستحيل |
| `PUT /api/settings` | فحوصات دور مفتتة (admin/dev) | «تعديل الإعدادات» كصلاحية مش موجودة |
| `/api/users` كله | `requireRoleBody("admin")` | «إدارة المستخدمين» كصلاحية مش موجودة |
| `GET /api/storage` | `requireRole("dev")` | «رؤية التخزين» في اللوحة بلا تأثير |
| `/api/perms` نفسها | `requireRoleBody("admin")` | اللي بيحرس الصلاحيات كان محروس بالدور |
| `GET/POST/PUT/DELETE /api/entries/*` | `requirePerm` ✅ | دول الوحيدين اللي كانوا صح (من R46) |

### 2. الواجهة: التطبيق عمره ما قرا الصلاحيات

grep على كل `public/app/*.js`: **مفيش ولا سطر واحد** بينادي
`/api/perms?me=1` ولا بيسأل «اليوزر ده مسموح له بإيه؟». الكود كله
بيسال بالدور بس (`isAdmin`/`isDev`). يعني حتى لو السيرفر كان بيفحص،
زرار «تحليل الأداء» في البوابة كان هيظهر لـ Nada وهي هتدخل على
شاشة فاضية/فشل تحميل — تجربة مكسورة من أول خطوة.

**الخلاصة:** لوحة الصلاحيات (R46) كانت بتكتب في `marib_perm`
والمكان الوحيد اللي بيقراها هو شاشة الأدمن نفسها. «زراير وخلاص»
بالظبط زي ما المالك شكّك.

## ثانيًا — الإصلاح: طبقتين (سيرفر + واجهة)

### الطبقة الأولى: السيرفر هو خط الدفاع الحقيقي

كل مسار اتلمّ على صلاحية الميزة بتاعته — نفس الحارس `requirePerm` /
`requirePermBody` اللي R46 بنتها وR55 بقى بيطبقها فعليًا:

```ts
// /api/data — كان أي يوزر داخل
const g = await requirePerm(req, "data.view", "view");     // GET
const g = await requirePermBody(req, "data.upload", "edit"); // POST
```

- `GET /api/data` → `data.view` (view) — **دي اللي بصد Nada**
- `POST /api/data` → `data.upload` (edit)
- `GET /api/manpower` → `manpower.view` · `POST /api/manpower` →
  `manpower.edit` (edit) والأكشن `import` لوحده → `manpower.import`
  (بنقرأ البادي الأول عشان نعرف الأكشن — requirePermBody مش بياكله)
- `GET /api/manpower/export` → `manpower.export` (view)
- `PUT /api/settings` → `settings.edit` (edit) فوق فحص dev-only
  القديم لـ `storage_quota`/`mhome`
- `/api/users`: GET → `users.manage` (view) والتغييرات → (edit)
- `GET /api/storage` → `storage.view` (view)
- `/api/perms`: القايمة → `users.manage` (view)، التعديل/المسح →
  (edit) — اللي بيوزع الصلاحيات بقى بيتمتح بصلاحية كمان

### ضبط الافتراضيات (`defaultForRole`)

الافتراضيات القديمة كانت فيها تناقضات كامنة من R46 — اتظبطت على
السلوك الفعلي القديم (صفر رجوعية):

- **dev** = edit على كل حاجة (زي ما هي)
- **admin** = edit على كل حاجة **بما فيها `users.manage`** — كانت
  «view» في الكود بينما الـ API فعليًا كان سايح للأدمن التحكم
  الكامل؛ لو طبقنا الـ view كان الأدمن هيتقفل فجأة
- **user** = view على كل حاجة **ما عدا** `users.manage` +
  `audit.view` + `storage.view` → **hidden** — كانت هترجع «view»
  وده كان هيفضح قايمة اليوزرين والسجل ومساحة الداتابيز لأي يوزر
  عادي أول ما الإنفورسمنت يتشغل

### الطبقة التانية: الواجهة بتسمع الصلاحيات

**طبقة صلاحيات جديدة في `app_auth.js`** (الملك بيده الجلسة):

- `loadPerms()` بعد كل login/boot بيجيب `/api/perms?me=1` (المستويات
  الفعّالة بعد دمج overrides الأدمن مع افتراض الدور)
- `can(feature, min)` معروفة للكل: `MaribAuth.can("data.view","view")`
- **fail-safe مش fail-open:** لو الفيتش فشل، الفالباك المحلي بنفس
  منطق `defaultForRole` — مفيش أبواب بتفتح بالغلط
- بتتمسح مع الخروج

**بوابة الأوضاع (تحليل الأداء / الاتزان):**

- زرار السطح الممنوع مش بيظهر أصلاً (`mgDash`/`mgMp`)
- الوضع المحفوظ في localStorage بيتحقق من الصلاحية قبل ما ينفذ —
  Nada اللي كانت آخر مرة على اللوحة بتدخل على المسموح بس
- لو السطحين مقفولين: العنوان بيتغير لـ«مفيش أي شاشات متاحة
  لحسابك» ومفضلك غير زرار الخروج
- `enterDash` نفسه فيه حارس (توست + رجوع للبوابة) — حماية مزدوجة

**كل أزرار الوصول بـ `refreshChrome` بالصلاحية مش بالدور:**

| الأزرار | الصلاحية |
|---|---|
| `btnUsers`/`tbUsersBtn`/`mgUsers`/`mpUsersBtn` | `users.manage` view |
| `btnSettings`/`tbSetBtn`/`mgSettings`/`mpSetBtn` | `settings.view` view |
| `tbDataBtn`/`mgData`/`mpDataBtn` | `data.view` view |
| `mgEntry` (الداتا إنتري) | `data.upload` edit |
| `btnSwap` (⇄) | السطحين الاتنين متاحين |

**الاتزان (`app_manpower.js`):** فلاج `ADMIN` اتغير من «دور أدمن»
لصلاحية `manpower.edit` edit — الفلاج ده موجود في 24 مكان (القلم،
التحديد، الحذف، الإضافة، الأقسام، الشواغر...) فكل أدوات التعديل
اتقفلت مرة واحدة. الاستيراد زرار لحاله (`manpower.import`) والتصدير
والتيمبلت (`manpower.export`) — وقايمة الاستيراد/التصدير كلها
بتختفي لو الاتنين مقفولين.

**صفحة البيانات:** `body.no-upload` للي ماعندوش `data.upload` edit →
CSS في آخر app.css بيقفل dropZone وأزرار الرفع والبوب أب — جدول
الشهور بيفضل ظاهر للقراءة.

**خانات الإعدادات:** كل خانة بصلاحيتها — targets بـ `settings.edit`
edit، groups/theme بـ `settings.view`، audit بـ `audit.view`، storage
بـ `storage.view`، الصلاحيات بـ `users.manage` view، ورئيسية المدير
dev بس (مفيش ليها مفتاح). حفظ الأهداف والتصنيفات بقى بيفحص نفس
صلاحية السيرفر.

**ترجمة:** 4 مفاتيح جداد (عربي/إنجليزي/تركي): `perm_denied` /
`perm_no_dash` / `perm_no_mp` / `perm_none`.

**Cache-bust:** كل السكريبتات + CSS اترفعوا `?v=r54` → `?v=r55`.
