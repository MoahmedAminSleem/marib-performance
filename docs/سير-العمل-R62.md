**Logging & Observability: قياس الاستعلامات + عدادات + stats حية في /api/health** — 17 سبتمبر 2026

> طلب المالك: «نفّذ الاتنين» في نفس السيشن — دي الجولة التانية (البند
> 5 والأخير من الأجندة الهندسية الخماسية). الأساس كان جاهز من R25
> (اللوج المنظم JSON بسطرين sink) وR54 (زمن فحص الصحة) — الجولة دي
> سدّت الفجوة اللي فاضلة: **مين بيقيس الاستعلامات؟ مين بيجاوب «آخر
> خطأ إيه وامتى»؟**

## الخلاصة في سطر

كل استعلام بيتقاس (عدد/زمن/بطيء>250ms/فاشل)، كل 5xx بيتعد ويتسجل
بسياقه، و`/api/health` بقى رابط واحد بيجاوب على كل أسئلة التشغيل —
والإثبات: **E2E 50/50** بنفس الـ 13 JSON + 5 XLSX **بالبايت** (صفر
تغيير سلوك) + فحوصات مراقبة حية.

## 1) إيه اللي اتعمل

### `src/lib/marib/stats.ts` (جديد) — عدادات خفيفة على globalThis

عدادات بتعيش مع العملية وبتتصفّر معها (مش بديل الأوديت — ده سجل
الأعمال الدائم، دي عدادات تشغيل لحظية):

| العداد | بيزود مين | معناه |
|---|---|---|
| `qCount / qMs` | db.ts — كل استعلام | عملنا كام استعلام وبكام زمن كلي |
| `qSlow` | اللي عدّت 250ms | إشارة زحمة (على Neon: أول استعلام بارد بعد خمول) |
| `qErrors` | الاستعلامات الفاشلة | مشاكل القاعدة |
| `srvErrors` | http.ts serverFail | أخطاء 5xx |
| `lastError/lastErrorAt` | noteError | **آخر خطأ إيه وامتى** — مقصوص 200 حرف، من غير passwords ولا قيم بارامترات |

### `db.ts` — قياس كل استعلام في مكان واحد

`timedQuery()` بتلفّ حوالين كل نداء (q() + جمل المعاملة في مسار pg
بتاع withTransaction): بتعدّ وبتقيس وبتسجل البطيء برأس الـ SQL بس
(80 حرف بعد تطبيع المسافات + **عدد** البارامترات مش قيمها — أسماء
الموظفين وما شابهها عمرها ما بتوصل اللوج) وبترمي لنفس المتصل.

### `http.ts` — serverFail بيسجّل بسياقه

نفس الرد بالبايت (`{error:"server"}` 500) — بس قبل ما يرجّعه:
`srvErrors++` + آخر خطأ بيتسجل `mod.method: message`. السطر المنظم
في اللوج موجود زي ما كان.

### `/api/health` — رابط واحد للتشغيل كله

```json
"stats": {
  "uptime_s": 214,
  "q": { "count": 3412, "slow": 2, "ms_total": 18740, "errors": 0 },
  "srv_errors": 0,
  "last_error": null,
  "mem": { "rss_mb": 148 },
  "node": "v22.14.0"
}
```

الأسئلة اللي المالك بيجاوب عليها بـ curl واحد: النسخة شغالة من قد
إيه؟ · عملت قد إيه استعلام وبكام زمن وفيه كام بطيء؟ · آخر خطأ إيه
وامتى؟ · الذاكرة قد إيه؟ (كمّلت سلسلة R57: boot بقى مرئي → stats
بقت مرئية). عدادات حية بالطبيعة زي boot — عشان كده تطبيع الـ E2E
بيشيلها (متجهز من R61).

### إيه اللي اتحط عن قصد بره النطاق

- **توقيت كل طلب HTTP على مستوى المسار:** على Vercel دي بتيجي من
  المنصة نفسها (Runtime Logs بيقولك المسار والزمن والحالة) — تكرارها
  في الكود كان هيضيف تشويش من غير قيمة. محليًا، slow-query + ms_total
  بيغطوا الجزء اللي بيبطيء فعلًا (القاعدة).
- **تصفير العدادات من API:** العدادات بتتصفّر مع العملية — نقاء
  بسيط أحسن من حالة إدارة تصفير محتاجة صلاحيات.

## 2) الإثبات — E2E 50/50

`scripts/e2e_r62.sh` (73 سطر — أول جولة بتستخدم مكتبة R61 من أول يوم):

- **صفر تغيير سلوك (18):** نفس 13 JSON + 5 XLSX **بالبايت** ضد
  baselines المرفوعة — stats بتتشال من health في الالتقاط (المطبّع
  كان متجهز من R61 عشان كده الجولة عدّت من أول تشغيلة).
- **بوابة الأنواع (4) + عقد الواجهة (3) + وظيفية (8) + UI (13):**
  كلها زي ما هي — اللوج الجديد ما لمسش أي مسار رد.
- **فحوصات المراقبة نفسها (4):**
  1. stats موجودة وشكلها سليم (uptime/q/mem/node + الأنواع).
  2. **العداد حي:** `q.count` قبل → نداءين manpower → بعد = زاد
     فعلًا (3412 → 3423 في التشغيلة).
  3. **الـ file sink:** `logs/marib.log` اتكتب في التشغيلة دي (اللوج
     القديم بيتشال قبل التشغيل عشان الفحص يكون صادق) + كل سطر JSON
     سليم فيه t/lvl/mod/msg (≥5 سطور).
  4. **الـ stdout sink:** نفس السطور في لوج السيرفر (ده اللي Vercel
     بيشوفه) + عتبة slow-query (250ms) موجودة في الكود.

## 3) إزاي تستخدمها يا مالك

```bash
# على Vercel (النسخة الحقيقية):
curl https://موقعك/api/health | python3 -m json.tool
# لو q.slow بيزيد باستمرار أو last_error مش فاضي → ابعتلي السطر
# لو mem.rss_mb بيكبر مع الوقت مع كل يوم تشغيل → ابعتلي الرقم
```

والسجل البطيء بيظهر في Vercel Dashboard → Deployments → Functions
Logs كسطر: `{"lvl":"warn","mod":"db","msg":"slow query","ms":812,
"head":"SELECT ... FROM marib_prod WHERE po_number = $1","params":1}`.

## دروس الجولة

- **جهّز التطبيع قبل الميزة:** الـ E2E كان بيشيل stats من health من
  R61 — عشان كده إضافة الميزة الحقيقية في R62 عدّت من أول تشغيلة
  من غير كسر المقارنة.
- **العدادات الحية بتنفع لما تكون مرئية:** عداد من غير مكان يشوفه
  فيه = ضجيج — /api/health هو المكان (نفس نمط boot بتاع R57).
- **قياس في طبقة واحدة (timedQuery) أحسن من قياس في كل مسار** —
  ملف واحد بيتغير، وكل الاستعلامات محسوبة حتى اللي جوه المعاملات.
